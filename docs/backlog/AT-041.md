# AT-041 · Validate the First Candidate Product Experience

**Status:** Completed  
**Epic:** Epic K · MVP Requirement Workflow  
**Completed:** 2026-08-17

## Objective

Validate the first candidate-oriented product increment without prematurely committing Atanor to a complete candidate journey, UI architecture or future backlog.

## Product Learning

The MVP must focus on the candidate. A curator is a conceptual internal/expert role whose functionality should only be introduced when required to provide or scale candidate value.

The current product model is based on a knowledge-first resolution flow:

```text
Convocatoria
     ↓
Requirement mentions
     ↓
Known Requirements
     ↓
Automatic resolution
     ↓
StudyRequirementSet
```

At this stage, convocatorias provide the index of requirements to study; Atanor does not yet generate the underlying knowledge represented by those requirements. Future iterations may need to support both pre-existing knowledge and knowledge acquisition/generation, but that decision is deliberately deferred.

## Validated Technical/Product Increment

Using the real `Programa_Archiveros_0.pdf` sample, Atanor currently:

1. Imports the PDF as a `Source`.
2. Extracts its textual content.
3. Discovers 25 structured requirement mentions corresponding to the 25 programme topics.
4. Resolves those mentions against a pre-existing set of known Requirements when exact deterministic matches are available.
5. Produces a `StudyRequirementSet` containing the resolved study requirements.

An isolated E2E test validates this complete initial segment using a temporary SQLite database and the real sample:

```text
Programa_Archiveros_0.pdf
        ↓
Source import
        ↓
Text extraction
        ↓
25 requirement mentions
        ↓
25 known Requirements
        ↓
Automatic resolution
        ↓
25 Study Requirements
```

The E2E test was added in commit `0f74540e0474c8add7b46819cb3409af57d9361c` (`AT-041 Add requirement workflow E2E test`).

## Validation Result

The initial workflow is technically validated. The current output can represent the study requirements of a supported convocatoria when the corresponding knowledge is already present in Atanor.

This is not yet sufficient evidence that the candidate experience is valuable. A list of resolved requirements is an internal capability and must now be evaluated as a product output: what must the candidate see, understand or receive beyond the raw requirement list for Atanor to solve a meaningful problem?

## Deliberately Deferred

- Complete Candidate Journey.
- Final UI or frontend architecture.
- Dedicated curator tooling.
- Candidate validation of Atanor's semantic decisions.
- Automatic knowledge generation or acquisition.
- Semantic matching beyond the current deterministic resolver.
- OCR/scanned-PDF support.
- Study planning, progress tracking, testing and adaptive learning.
- Detailed future task definitions that are not justified by evidence from the next iteration.

## Development Strategy Established by AT-041

Atanor is now explicitly developed through **product-led mini-MVP iterations**.

Each iteration should:

1. formulate a concrete product hypothesis;
2. define the smallest useful experience capable of testing it;
3. implement only the technical capabilities required by that experience;
4. validate the result with a realistic example;
5. use the resulting evidence to define the next iteration.

The backlog should therefore describe the current hypothesis and validated outcome rather than attempting to predict a long sequence of implementation tasks while the product is still immature.

## Next Step

Do not create a predefined AT-042 implementation yet. The next mini-MVP should be derived from the product evaluation of the current `StudyRequirementSet` output, specifically:

> **What is the minimum information a candidate must receive after providing a convocatoria for Atanor's answer to "What do I need to study?" to be genuinely useful?**

The next task should be defined from the answer to that question.
