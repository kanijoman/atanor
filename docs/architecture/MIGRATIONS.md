# Database Migrations

Atanor uses Alembic to evolve the SQLAlchemy persistence schema.

## Rules

- The persistence model is the desired schema; migrations define the controlled transition between persisted states.
- Every persistent schema change must be represented by an explicit, reviewed migration.
- `Base.metadata.create_all()` is not used to evolve a persistent database. It remains available for isolated tests where appropriate.
- Autogenerated migrations are candidates only. They must be reviewed and adjusted manually before being applied.
- Migrations must be reversible when the underlying database operation supports a safe reversal.

## Workflow

From `backend/`:

```text
uv run alembic revision --autogenerate -m "describe the schema change"
uv run alembic upgrade head
```

Review the generated revision before committing it. To verify a rollback:

```text
uv run alembic downgrade -1
```

The initial migration establishes the baseline persistence schema represented by the current SQLAlchemy models. It does not attempt to reconstruct the historical evolution of the project.

## Tests

Migration tests create an isolated SQLite database, apply all migrations to `head`, verify the resulting schema, and then downgrade to `base`.

This gives us a small executable guarantee that a fresh database can be built and rolled back exclusively through migrations.
